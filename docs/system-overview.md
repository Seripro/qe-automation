# QE Calculator の仕組み

この文書は、進捗報告で「ブラウザからQEをどう動かしているか」と聞かれたときに説明するための資料である。

- 構成図: [qe-webapp-architecture.html](architecture/qe-webapp-architecture.html)
- 採用判断: [ADR-0005](decisions/0005-use-application-queue-on-mdx.md)、[ADR-0006](decisions/0006-use-anonymous-browser-sessions-for-mvp.md)、[ADR-0007](decisions/0007-fail-interrupted-jobs-after-worker-restart.md)

## 一文でいうと

ブラウザがQEを直接実行するのではなく、計算要求をAPI経由でSQLiteの待ち行列へ保存し、mdx-server上の**単一ワーカー**が一件ずつQEを実行する仕組みである。

## 構成要素と役割

| 要素 | 主な技術 | 役割 |
| --- | --- | --- |
| ブラウザ | Webブラウザ | ZIPの登録、状態・ログ・図の表示、キャンセル要求を行う。 |
| フロントエンド | React / Vite | ブラウザ画面を提供する。開発時は`127.0.0.1:5173`で動く。4秒ごとにAPIから状態を取り直す。 |
| API | FastAPI | ZIPを受け取り、ジョブ情報を作成・閲覧・キャンセルする。QE計算そのものは実行しない。 |
| ジョブDB | SQLite | ジョブの状態、時刻、専用作業ディレクトリ、実行プロセス情報を永続化する。 |
| ワーカー | Pythonプロセス | 最も古い待機ジョブを一件取得し、QE用スクリプトを順に実行する。 |
| 計算スクリプト | Bash / Python | ZIP検証、SCF、Band、NSCF/PDOS、SeeK-pathによるk点経路作成、図の作成を担う。 |
| QE | `pw.x`、`bands.x`、`projwfc.x` | 実際の第一原理計算を行う。 |

## 通常時の処理の流れ

1. 利用者が物質名ラベルと`.zip`ファイルをブラウザから送る。
2. FastAPIはラベル・拡張子・アップロードサイズを検査し、サーバー生成のジョブ専用ディレクトリへZIPを保存する。
3. APIはSQLiteへ`QUEUED`状態のジョブを保存し、ブラウザへジョブ情報を返す。
4. ワーカーがSQLiteから最も古い`QUEUED`ジョブを排他的に取得する。最初の状態は`VALIDATING`である。
5. ZIPの安全性と`PWscf/pwscf.in`の存在を確認する。
6. SCF → Band → NSCF/PDOSの順に外部スクリプトを実行する。前段が失敗したら、後段は実行しない。
7. `bands.png`と`pdos.png`が存在することまで確認できたら、ジョブを`COMPLETED`にする。
8. ブラウザはAPIを定期取得して状態を表示し、完了後に画像とログを表示する。

計算本体はHTTPリクエスト中では動かない。したがって、ブラウザを閉じても、API画面を再読み込みしても、ワーカーが生きている限り計算は継続する。

## 状態遷移

```text
QUEUED
  ↓
VALIDATING
  ↓
SCF_RUNNING
  ↓
BAND_RUNNING
  ↓
PDOS_RUNNING
  ↓
COMPLETED
```

各段階から、`FAILED`、`CANCELLED`、`TIMED_OUT`へ遷移し得る。これらは終端状態であり、後続計算には進まない。

- `FAILED`: ZIP不備、QEの終了コード異常、必須成果物不足など
- `CANCELLED`: 利用者が停止を要求した
- `TIMED_OUT`: 一つの計算段階が設定時間を超えた

## なぜ待ち行列とワーカーを分けたか

QE計算は数十秒から長時間かかり、CPU・メモリを消費する。Web APIがリクエストごとに直接QEを起動すると、複数人の操作で同時に計算が走り、サーバー資源を使い切るおそれがある。

そのため、初期MVPでは同時実行を1件に固定している。2人目以降の要求はSQLiteの`QUEUED`として保存され、先の計算が終わってから実行される。PBSは使わず、アプリ自身が小さな待ち行列を持つ方式である。

## 入力と作業ディレクトリ

利用者が付ける物質名ラベルは表示用であり、一意である必要はない。内部ではUUIDのジョブIDと専用ディレクトリで区別するため、同じ`MgB2`というラベルの計算を複数投入しても結果は混ざらない。

アップロード時のZIP名も自由である。サーバー側で保存名を`PWscf.zip`に統一する。ただし、ZIP内には`PWscf/pwscf.in`が必要である。

ジョブごとの概念的な配置は次の通りである。

```text
webapp/runtime/jobs/<server-generated-id>/
├── upload/PWscf.zip       # 利用者が送った入力
├── run/PWscf/             # QEが使う作業領域
│   ├── scf.out
│   ├── band.out
│   ├── nscf.out
│   ├── pdos.out
│   ├── bands.png
│   └── pdos.png
└── worker.log             # 段階ごとの実行ログ
```

## 安全性とジョブの識別

- 物質名ラベルは英数字、`_`、`-`だけを許可し、シェル文字列として連結しない。
- 外部コマンドは引数配列で起動する。
- ZIPは展開前にパストラバーサルなどを検査する。
- ブラウザにはサーバー発行の匿名IDを`HttpOnly` Cookieで保持し、自分が作成したジョブだけを一覧にする。
- 個別ログインや大学SSOは初期MVPの範囲外である。

匿名Cookieは厳密な本人認証ではない。学校Wi-Fiからだけ接続できるというネットワーク前提と合わせた、研究室・授業向けの軽量な方式である。

## キャンセル、タイムアウト、再起動

### キャンセル

待機中なら直ちに`CANCELLED`にする。実行中ならワーカーが次の監視周期で要求を検出し、QEを含むプロセスグループへ終了要求を送る。猶予後も残る場合は強制終了する。

### タイムアウト

SCF、Band、PDOSの各外部コマンドには時間上限がある。上限を超えた段階は停止され、`TIMED_OUT`になる。これはジョブ全体の時間ではなく、段階ごとの上限である。

### API再起動

ジョブ状態と作業ディレクトリはSQLiteに保存されているため、API・フロントエンドを再起動しても過去の履歴を読める。

### ワーカー異常停止

途中から安全に計算を再開できるとは限らないため、ワーカー再起動時に進行中だったジョブは`FAILED`にし、「再投入してください」と示す。待機中ジョブはそのまま残り、新しいワーカーが処理する。

同じ実行データ領域に複数ワーカーが同時に動かないよう、ワーカーは排他ロックを取得してから起動する。

## 開発時の起動

```bash
cd ~/qe-automation
make web-dev
```

このコマンドは、FastAPI、ワーカー、Vite開発サーバーをまとめて起動する。開発用にローカルホストだけで待ち受ける構成であり、公開用の常駐サービス設定ではない。

## 現在の制約

- 入力は検証済みZIPのみであり、CIFからの入力生成や画面上の計算パラメータ編集はしない。
- 計算が正常終了しても、物理的な妥当性・収束性は別途確認が必要である。
- 同時実行は1件である。授業利用時の待ち時間は未評価である。
- 利用者単位の投入上限、ZIP容量上限、成果物の保存期間、学校Wi-Fi制限の実効性は未決定である。
- NaではBand段階にQEの数値エラーがあり、対応物質の範囲はまだ検証途中である。

## 報告での短い説明例

> ブラウザから入力ZIPを送ると、APIが計算要求をSQLiteへ保存します。別プロセスのワーカーが要求を一件ずつ取り出し、mdx-server上でQEのSCF・Band・PDOSを順番に実行します。途中で失敗・キャンセル・時間切れになれば後続段階へ進めず、状態とログを残します。完了後は生成したバンド図とPDOS図をブラウザで表示します。
