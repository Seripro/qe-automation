# QE自動計算Webアプリ 要件定義書

## 概要

Quantum Espresso のバンド計算・PDOS計算を、ブラウザからZIPファイルをアップロードするだけで実行し、結果（bands.png, pdos.png）を表示・ダウンロードできるWebアプリケーション。

## 技術スタック

- バックエンド: FastAPI (Python)
- フロントエンド: React (TypeScript)
- 計算実行: 既存シェルスクリプト（qe_auto_kp.sh 相当）を subprocess で呼び出し
- ジョブ管理: PBS (qsub) — WebサーバーとPBSが同一マシン上
- リアルタイム通信: WebSocket (進捗通知)

---

## 機能要件

### 1. ジョブ投入

| 項目 | 内容 |
|------|------|
| 入力 | ZIPファイル (PWscf.zip)、物質名 (DIR_NAME) |
| バリデーション | ZIP内に `pwscf.in` が存在すること |
| 出力 | ジョブID（UUID）を返す |

### 2. 進捗表示

計算のステージごとに進捗を表示する:

1. `UPLOADING` — ファイルアップロード中
2. `SCF_RUNNING` — SCF計算実行中
3. `SCF_DONE` — SCF完了、バンド入力ファイル生成済み
4. `BAND_RUNNING` — バンド計算実行中
5. `BAND_DONE` — バンド図生成完了
6. `PDOS_RUNNING` — PDOS計算実行中
7. `COMPLETED` — 全計算完了（bands.png + pdos.png 生成済み）
8. `FAILED` — エラー終了

### 3. 結果の閲覧

- bands.png と pdos.png をブラウザ上で表示
- 各画像の個別ダウンロード
- 計算ログ（scf.out, band.out, pdos.out）の閲覧

### 4. ジョブ履歴

- 過去のジョブ一覧（物質名、状態、投入日時）
- 結果の再閲覧

## 課題と対処方針

### 課題1: 長時間ジョブの進捗監視（ポーリング問題）

**問題**: PBS計算は数分〜数時間かかる。HTTPリクエストでポーリングするとサーバー負荷が高く、リアルタイム性も低い。

**対処**: WebSocket を使い、サーバー側でプッシュ通知する。

```
[Browser] <--- WebSocket --- [FastAPI] <--- ファイル監視 --- [PBS Job]
```

- バックエンドにジョブごとの監視タスクを作成（asyncio.Task）
- 監視タスクは `scf.out` 等のファイルを定期チェック（10秒間隔、サーバー内ローカルI/Oなので軽量）
- ステージ遷移を検知したらWebSocket経由でクライアントに即プッシュ
- クライアントが切断→再接続した場合は、現在のステータスをREST API (`GET /jobs/{id}`) で取得してリカバリ

**フォールバック**: WebSocket接続が不安定な環境向けに `GET /jobs/{id}/status` のポーリングAPIも提供（30秒間隔を推奨）。

---

### 課題2: プロセス寿命の管理

**問題**: 現在のスクリプトは `while ! grep -q "JOB DONE"` で無限ループ待機する。Webサーバープロセスが再起動すると監視が途切れる。

**対処**:

- ジョブ状態をファイルベースのDB（SQLite）に永続化
- 各ジョブのメタデータ: `{id, dir_name, work_dir, status, pbs_job_id, created_at, updated_at}`
- サーバー起動時に `status != COMPLETED && status != FAILED` のジョブを再スキャンし、監視タスクを再作成
- 監視タスク自体は冪等（途中から再開可能）— ファイルの現在の状態で次ステップを判断

---

### 課題3: 同時実行とリソース制御

**問題**: 複数ユーザーが同時にジョブを投入するとPBSキューが溢れる可能性。

**対処**:

- アプリ側で同時実行数を制限（デフォルト: 最大3ジョブ並行）
- 超過分はアプリ内キューで待機させ、完了次第自動投入
- PBSキュー自体のリソース管理にも依存するため、二重制御

---

### 課題4: エラーハンドリング

**問題**: MKLライブラリエラー、ディスク容量不足、PBS拒否など多様な失敗パターン。

**対処**:

| 失敗パターン | 検知方法 | ユーザーへの表示 |
|---|---|---|
| qsub 失敗 | subprocess の return code | 「ジョブ投入に失敗しました」+ エラー出力 |
| 計算中エラー | `*.out` ファイル内の `Error` / `CRASH` 文字列 | 「SCF計算がエラーで停止しました」+ 該当行 |
| タイムアウト | 設定時間（デフォルト6時間）超過 | 「計算がタイムアウトしました」 |
| ファイル不在 | 期待するファイルが生成されない | 「出力ファイルが生成されませんでした」 |

---

### 課題5: ファイルパスとセキュリティ

**問題**: ユーザー入力の物質名（DIR_NAME）がシェルに渡るため、コマンドインジェクションのリスク。

**対処**:

- DIR_NAME は英数字とハイフンのみ許可（正規表現: `^[A-Za-z0-9_-]{1,50}$`）
- 作業ディレクトリはサーバー側で一意なパスを生成（`$HOME/work/{uuid}/`）
- アップロードファイルサイズ上限: 50MB
- シェルスクリプト呼び出し時は `shlex.quote()` でエスケープ

## API設計

```
POST   /api/jobs              ジョブ投入 (multipart: zip + dir_name)
GET    /api/jobs              ジョブ一覧
GET    /api/jobs/{id}         ジョブ詳細（ステータス含む）
GET    /api/jobs/{id}/status  ステータスのみ（軽量ポーリング用）
GET    /api/jobs/{id}/results バンド図・PDOS画像のURL
GET    /api/jobs/{id}/logs    計算ログ取得
DELETE /api/jobs/{id}         ジョブキャンセル（qdelを実行）
WS     /api/ws/jobs/{id}     WebSocket（進捗プッシュ）
```
