シェルスクリプトで自動化したかったけどなんかエラー出て困ってた。結局解決した。
今回のトラブルシューティングとスクリプト構築のプロセスは、HPC（ハイパフォーマンスコンピューティング）環境での自動化における「あるある」が詰まった非常に価値のある経験だったと思います。
次回以降、別の計算環境や新しい物質で計算を行う際の「最強の虎の巻」として、今回のチャットの要点と教訓をまとめました。
1. 達成したこと：汎用的なQE自動化パイプラインの構築
手作業で行っていたJupyter Notebookのコマンド群を、全物質対応の2ステップ自動化シェルスクリプトに昇華させました。
• 動的PDOS抽出: 物質（Zn, Siなど）が変わっても、生成されたファイル名から自動で元素と軌道（s, p, d）を読み取って合算・プロットするロジックを実装しました。
• ジョブの監視機能: qsub で投げた計算が完了する（scf.out 等に JOB DONE が出る）まで待機し、自動で次のステップに進む仕組みを作りました。
2. 計算ジョブ運用の鉄則
サーバー上で長時間かかる処理を走らせる際のベストプラクティスを確立しました。
• 裏側で放置実行する (nohup) ターミナルを閉じても監視スクリプトを殺さないため、実行時は必ず以下を使います。 nohup bash スクリプト名.sh > run.log 2>&1 &
• やり直す前のリセット (kill と rm -rf) 途中で計算を止める場合は、裏で動いている監視スクリプトを jobs で確認して kill %1 で止め、中途半端な出力フォルダを rm -rf で綺麗に消してから再実行します。
3. 今回の最大の罠と教訓（ライブラリエラーの真実）
【現象】
pw.x の計算が libmkl_scalapack_lp64.so.1: cannot open shared object file というエラーで即座に強制終了してしまう現象が連続しました。
【原因と解決策】
1. 環境変数の引き継ぎ問題: ログイン画面（普段のターミナル）で見えているパス（LD_LIBRARY_PATH）が、PBSの裏側の計算ノードには自動で引き継がれませんでした。
2. バージョンのミスマッチ（最大の原因）: Quantum Espresso (pw.x) は**古いIntel MKL（2021.3.0）**を使ってコンパイル（構築）されていたのに対し、現在ログインしている環境（intelpython-python3.7）には新しいMKL（2025.3）のパスが設定されていました。そのため、いくら環境変数を引き継いでも「探しているファイルがない！」とエラーになっていました。
3. 結論: ジョブスクリプトの中で、「pw.xが本当に欲しがっている古いバージョンの絶対パス」を直接 LD_LIBRARY_PATH にねじ込み、mpiexec -genv で計算ノードに強制的に渡すことで解決しました。
4. 今後のための「お助けコマンド辞典」
今後、別のエラーが起きたときに原因を特定するためのコマンド群です。
• ジョブの状態確認とキャンセル • qstat -u $USER : 自分のジョブがキュー（Q）か実行中（R）か確認する。 • qdel ジョブID : おかしくなったジョブをキャンセルする。
• エラーの原因究明 • tail -n 20 scf.out : 出力ファイルの末尾を見て、正常終了（JOB DONE）かエラーか確認する。 • cat scf.sh.e* : PBS自体が出力したエラーログを確認する。
• ライブラリ（.soファイル）が見つからないと言われたら • ldd /パス/pw.x : プログラムが「どの場所の、どのバージョンのライブラリ」を要求しているか（not found になっていないか）を調べる。 • find /opt -name "ファイル名" 2>/dev/null : サーバー全体のどこにそのファイルが隠れているか強引に探し出す。
このまとめをメモ帳などに残しておけば、次に新しいサーバーを使ったり、別のプログラム（VASPやLAMMPSなど）で同様のエラーに遭遇したりした際にも、真っ先に原因を特定できるはずです。
