# ジョブ待ち行列・直接実行ワーカー仕様案

- 状態: **提案中**
- 作成日: 2026-11-21
- 関連判断: [ADR-0005: mdx-server上のアプリ側待ち行列で直接実行する](decisions/0005-use-application-queue-on-mdx.md)
- 関連画面仕様: [GUIワークフロー仕様案](gui-workflow-spec.md)

## 1. 目的

授業利用を想定し、Webアプリが受け取った計算要求を永続的な待ち行列へ保存し、mdx-server上のワーカーが安全に一件ずつ実行する。HTTPリクエストやブラウザ接続の継続にQE計算を依存させない。

初期の同時実行数は **1件** とする。将来、CPU・メモリ使用量と待ち時間を測定したうえで、設定値として増やす。

## 2. 処理全体

```text
ブラウザ
  ↓ ZIPと物質名ラベルを送信
Web API
  ↓ ZIP検査・ジョブ情報を永続化
QUEUED
  ↓ ワーカーが空き枠を確認
VALIDATING
  ↓ 安全な展開・入力内容の検査
SCF_RUNNING
  ↓ 成功時のみ
BAND_RUNNING
  ↓ 成功時のみ
PDOS_RUNNING
  ↓ 成功時のみ
COMPLETED
```

どの段階でも、エラー、利用者キャンセル、時間制限超過があれば後続段階を実行せず終了する。

## 3. ジョブ状態

| 状態 | 意味 | 次に遷移できる状態 |
|---|---|---|
| `QUEUED` | 受理済みで、ワーカーの空き待ち | `VALIDATING`, `CANCELLED` |
| `VALIDATING` | ZIPの検査・展開・入力確認中 | `SCF_RUNNING`, `FAILED`, `CANCELLED` |
| `SCF_RUNNING` | `pw.x` によるSCF実行中 | `BAND_RUNNING`, `FAILED`, `CANCELLED`, `TIMED_OUT` |
| `BAND_RUNNING` | k点経路作成、バンド計算、描画中 | `PDOS_RUNNING`, `FAILED`, `CANCELLED`, `TIMED_OUT` |
| `PDOS_RUNNING` | NSCF、PDOS、集計、描画中 | `COMPLETED`, `FAILED`, `CANCELLED`, `TIMED_OUT` |
| `COMPLETED` | 全成果物を確認して公開可能 | なし |
| `FAILED` | 検証・実行・成果物確認の失敗 | なし |
| `CANCELLED` | 利用者または管理者が停止 | なし |
| `TIMED_OUT` | 段階またはジョブ全体の時間上限超過 | なし |

`COMPLETED`、`FAILED`、`CANCELLED`、`TIMED_OUT` は終端状態である。終端状態のジョブを再実行する場合は、既存ディレクトリを再利用せず、新しいジョブとして登録する。

## 4. 永続化する情報

ジョブ情報はWebサーバー・ワーカーの再起動後にも残るデータベースへ保存する。

| 項目 | 用途 |
|---|---|
| `id` | 推測困難なジョブID。専用作業ディレクトリ名にも使う。 |
| `owner_id` | サーバー発行の匿名ブラウザID。`HttpOnly` Cookieと照合する。 |
| `view_token_hash` | ジョブ詳細の閲覧トークンをハッシュ化して保存する。生のトークンは保存しない。 |
| `material_label` | 表示・履歴用の安全なラベル。英数字、`_`、`-` のみ。 |
| `input_zip_name` / `input_zip_sha256` | 入力の追跡と再現性確認。 |
| `state` / `state_reason` | 現在状態と失敗・停止理由。 |
| `queue_position` | 待機中に表示する順番。永続値ではなく取得時に計算してよい。 |
| `created_at` / `started_at` / `finished_at` / `updated_at` | 履歴、待ち時間、実行時間の確認。 |
| `work_dir` | ジョブ専用の作業ディレクトリ。 |
| `current_stage` | 実行・復旧・画面表示に使う段階名。 |
| `process_id` / `process_group_id` | 実行中のQEプロセス群を停止・再確認するための情報。 |
| `exit_code` | 実行失敗の判定補助。 |
| `artifacts` | 図、ログ、入力、生成データの安全な相対パス一覧。 |

利用者の入力をシェル文字列へ連結しない。外部コマンドは引数配列で起動し、作業ディレクトリはジョブIDから作る。

## 5. ワーカーの責務

ワーカーは次を繰り返す。

1. 実行枠に空きがあれば、最も古い `QUEUED` ジョブを一件だけ排他的に取得する。
2. `VALIDATING` へ遷移し、ZIPのパス・容量・展開後容量・`pwscf.in`・擬ポテンシャルを確認する。
3. ジョブ専用ディレクトリにのみ展開し、SCFを開始する。
4. 各段階の終了コード、`JOB DONE`、必須成果物を確認してから次段階へ進む。
5. 標準出力・標準エラー・状態・開始・終了時刻・成果物を保存する。
6. 利用者のキャンセル要求、段階タイムアウト、全体タイムアウトを監視する。
7. 終端状態へ遷移し、実行枠を解放する。

ワーカーはWeb APIとは別プロセスとして動かす。Web API再起動だけで実行中QEプロセスを孤児化させない。

## 6. キャンセル・タイムアウト

### キャンセル

- `QUEUED` のキャンセルは、状態を直ちに `CANCELLED` にする。
- 実行中のキャンセルは、まず新しい段階へ進むことを止め、対象のプロセスグループへ終了要求を送る。
- 猶予時間後も終了しない場合だけ強制終了する。
- 生成済みログと成果物は削除せず、状態と停止理由を残す。

### タイムアウト

- SCF、バンド、PDOSの段階別上限と、ジョブ全体の上限を設定値として持つ。
- 値はmdx-serverでの実測時間、授業の利用時間、利用可能資源を確認してから決める。現時点では未採用。
- 超過時はキャンセルと同じ停止手順を行い、状態を `TIMED_OUT` にする。

## 7. 再起動時の扱い

Web APIまたはワーカー起動時に、終端状態でないジョブを確認する。

- `QUEUED` はそのまま待ち行列へ戻す。
- 実行中のジョブは、保存したプロセスグループが存在するか、ログ・成果物の更新が続いているかを確認する。
- 実行プロセスを安全に確認できない場合は、推測で成功扱いにせず `FAILED` とし、理由を「再起動後に実行状態を確認できない」と記録する。

復旧の詳細な実装・許容条件は、バックエンド設計時に小さな実験で検証する。

## 8. 未決定事項

1. ブラウザ単位の待機・実行ジョブ数、ZIP容量、展開後容量の上限。
2. 段階別・全体タイムアウト値と、キャンセル時の猶予時間。
3. 作業結果の保存期間と、期限切れ成果物の削除方針。
4. mdx-serverの実測に基づく同時実行数の上限。
5. 学校Wi-Fi限定のネットワーク制限が、公開環境で実際に有効かの確認。
