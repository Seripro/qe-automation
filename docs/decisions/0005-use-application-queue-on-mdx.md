# ADR-0005: mdx-server上のアプリ側待ち行列で直接実行する

- 日付: 2026-11-21
- 状態: 採用
- 決定者: 研究者（ユーザー）とAIアシスタント
- 関連資料: [ADR-0004](0004-stage-cli-workflow-before-pbs.md)、[GUIワークフロー仕様案](../gui-workflow-spec.md)、[マイルストーン](../milestones.md)

## 背景・課題

将来、授業で最大90人程度が利用する可能性がある。一方、研究用・サービス用の実行先は教員から貸与された `mdx-server` とし、研究室の共有PBSサーバー `nordstrom` は他メンバーの研究用途のため使わない。`mdx-server` にはPBSクライアント・サーバーは構成されていない。

WebリクエストごとにQEを直接起動すると、同時実行による資源競合と長時間プロセスの追跡ができない。

## 検討した選択肢

### 選択肢1: PBSをmdx-serverへ導入する

- スケジューラの機能を利用できる。
- 単一サーバーのためにPBSサーバー・デーモン・キュー・権限を運用する負担が大きい。

### 選択肢2: nordstromのPBSへ投入する

- 共有スケジューラを利用できる。
- サービスの計算先として共有研究サーバーを使わない方針と矛盾する。

### 選択肢3: Webアプリの永続待ち行列とワーカーでmdx-server上のQEを直接実行する

- 実行先をmdx-serverに限定したまま、待機・実行・失敗・キャンセル・成果物をアプリで管理できる。
- 初期は同時実行数を1件に制限し、計測後に設定値として増やせる。
- PBS固有の運用を初期MVPへ持ち込まない。

## 判断

**選択肢3を採用する。**

MVPでは、Webアプリが永続的なジョブ待ち行列を保持し、mdx-server上のワーカーがQEを直接実行する。初期の同時実行数は1件とする。WebアプリのHTTPリクエスト内でQEを実行せず、独立したワーカーがキューからジョブを取得して実行する。

## 影響・トレードオフ

- アプリはジョブ状態、プロセスID、ログ、タイムアウト、キャンセル、Webアプリ再起動後の回復可能性を永続化する。
- 授業利用を想定し、認証またはアクセス制限、アップロード容量、利用者ごとの待機・実行ジョブ上限を実装前に決める。
- 直接実行CLIは開発・運用確認用として維持する。
- PBSは、将来別の共有計算基盤を採用する場合の拡張候補とする。ADR-0004のPBS追加方針は、この判断により置き換える。

## 後で見直す条件

- mdx-serverの資源・運用規則が授業利用に適さない場合。
- 実測に基づき、同時実行数1件では授業運用の待ち時間が許容できない場合。
- 別の共有スケジューラまたは計算基盤の利用が許可・決定された場合。
