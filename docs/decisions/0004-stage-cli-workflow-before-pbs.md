# ADR-0004: PBS対応前に一コマンドCLIワークフローを整備する

- 日付: 2026-11-21
- 状態: 採用
- 決定者: 研究者（ユーザー）とAIアシスタント
- 関連資料: [次回の作業](../next-action.md)、[GUIワークフロー仕様案](../gui-workflow-spec.md)、[MgB₂の実験記録](../experiments/mgb2/2026-11-21-band-pdos.md)

## 背景・課題

SiとMgB₂で、直接実行によるSCF → バンド構造 → NSCF/PDOSの計算フローが成立した。しかし現在は段階ごとにコマンドを実行する必要があり、物質ごとの入力ZIPの置き場所も一貫していない。

最終的にはPBSによる資源管理・ジョブ監視を目指すが、PBS対応を先に進めると、計算フローの問題とスケジューラ連携の問題を区別しにくい。また、利用者にとっての「入力を指定して一回実行する」という操作は、直接実行・PBS実行のどちらでも共通にできる。

## 検討した選択肢

### 選択肢1: PBS対応を先に実装する

- 最終的なMVP仕様へ早く近づける。
- `qsub`、`qstat`、`qdel`、キュー待ち、ジョブID永続化、再接続を同時に扱う必要があり、計算フロー自体の検証が複雑になる。

### 選択肢2: 直接実行専用の一コマンド化を行い、後でPBS用に作り直す

- 直近の操作は楽になる。
- 実行方式に強く結び付けると、PBS移行時にユーザー操作・状態管理を作り直す可能性がある。

### 選択肢3: 実行方式を分離した一コマンドCLIを先に整備し、後からPBS実行器を追加する

- 入力の解決、作業ディレクトリ作成、段階の順序、成果物の表示を直接実行・PBS実行で共通化できる。
- 最初の実行器は直接実行とし、PBS対応時に実行器を差し替える。
- 初期設計に実行方式の境界を設ける必要がある。

## 判断

**選択肢3を採用する。**

PBS対応の前に、物質別入力を解決してSCF → バンド → PDOSを一回のコマンドで順次実行するCLIを整備する。初期実行器は直接実行とするが、CLIの利用方法とワークフロー状態はPBS固有の情報に依存させない。PBSは次段階で実行器として追加する。

入力ZIPのサーバー上の標準配置は、次の形を採用する。

```text
~/qe-inputs/
└── <material-label>/
    └── PWscf.zip
```

`<material-label>` は物理的な計算条件ではなく、入力と実行履歴を整理するための安全な識別子とする。許可文字は英数字、`_`、`-` に限る。通常はASCII化した化学式を使い、`MgB2`、`Si` のように命名する。同じ化学式で複数の基準入力を扱う場合は、結晶相や目的を追加して区別する（例: `TiO2-rutile`、`MgB2-test1`）。

計算の実際の構造・元素・擬ポテンシャル・パラメータは、ラベルではなく `PWscf.zip` 内の `pwscf.in` を正とする。

## 理由

- 利用者が必要とする操作を、物質名指定と一回の実行へ減らせる。
- 入力ZIPをリポジトリ外に保管し、Git管理対象と実行用バイナリ入力を分離できる。
- 直接実行で計算フローの失敗を切り分けてからPBS連携の実装・検証に進める。
- 将来GUIが同じワークフローを呼び出す際、実行方式への依存を狭められる。

## 影響・トレードオフ

- 直接実行中は、同時実行数・タイムアウト・キャンセル・Webサーバー再起動後の扱いを別途制限・実装する必要がある。
- PBS対応後は、CLIの利用方法を維持しつつ、`qsub`、`qstat`、`qdel` とPBSジョブIDの永続化を実装する。
- `material-label` は表示・パス・メタデータ用であり、化学式として厳密である必要はない。ただし再現性のため、何を指す入力かが分かる名前を付ける。

## 後で見直す条件

- サーバーの運用規則により直接実行が許可されない、または資源競合が発生する場合。
- 複数利用者・複数入力バージョンの管理に、物質ラベルだけでは不足する場合。
- GUIの対象ユーザーや認証・入力管理方式が決定し、入力保管場所を変更する必要がある場合。
